# Сбор за открытие счёта (opening fee)

> Для команды регистрации (`app.altery.com/n/registration-corporate`) и операций.
> Код: `api/opening-fee.js`, `lib/opening-fee.js`, `lib/opening-fee-token.js`.

---

## 1. Политика (решение основателя, 2026-09-23)

| | |
|---|---|
| Сумма | **£100**, GBP для всех регионов (UK / EU / MENA) |
| Когда | после результата «вам подходит», до регистрации |
| Как | через Stripe: карта, Apple Pay или Google Pay; списание сразу (automatic capture) |
| За что | **одна попытка заявки** (одна оплата = одна заявка) |
| Привязка к компании | **при первом использовании в регистрации**: оплату забирает первая заявка, пришедшая с токеном; вторую заявку с той же оплатой регистрация не принимает |
| Возврат | **не возвращается ни в каком случае**, включая отказ по KYB и отказ клиента |
| Срок | не истекает: оплатил — может закончить регистрацию когда угодно |
| Кто не видит | заблокированные страны/отрасли (им показывается мягкий отказ ещё до результата) |
| Крипто-клиенты | платят так же, как все |
| Версия условий | `2026-09-23` (`metadata.terms_version`) |

Клиент видит условия прямо над галочкой и обязан её поставить; время согласия
пишется в `metadata.terms_accepted_at`. Это доказательная база при chargeback.

**Уточнение того же дня (2026-09-23):** пейвол **не спрашивает** юридическое
название и регистрационный номер компании. Клиент вводит только рабочий e-mail;
страну регистрации компании чекер уже знает из первого вопроса опроса.
Компания становится известна только в регистрации, и там же оплата к ней
привязывается (раздел 5).

## 2. Как это работает

1. Результат «подходит» → «Continue to account opening» → пейвол. Комиссия
   объявляется структурой интерфейса, а не сносками: шаг «Account opening»
   в сайдбаре («£100 · one-time»), блок «Your costs» из двух ячеек на
   странице результата и в сводке пейвола («Today · one-time £100 / After
   activation · monthly £100 Pro plan»: у тарифа Pro та же цена, поэтому
   метки времени разводят два платежа), строка комиссии на карточках
   сравнения тарифов и текст кнопки.
2. Клиент вводит **рабочий e-mail**, ставит галочку согласия и платит картой,
   Apple Pay или Google Pay. Страна регистрации компании берётся из опроса.
3. Сервер создаёт PaymentIntent в Stripe (£100, тип оплаты `card`: Apple Pay и
   Google Pay работают поверх карты) и записывает в `metadata` e-mail, страну
   компании, тариф и согласие с условиями. Компании в Stripe нет.
4. Stripe.js подтверждает оплату (при необходимости 3-D Secure, возможен
   редирект в банк и обратно).
5. Сервер **сам** перечитывает PaymentIntent в Stripe и проверяет:
   `status = succeeded`, `amount = 10000`, `currency = gbp`,
   `metadata.kind = account_opening_fee`. Только тогда выдаёт подписанный токен.
6. Редирект на регистрацию с токеном `opening` и `email` в URL.
7. Регистрация проверяет токен и **привязывает оплату к первой заявке**, которая
   с ним пришла (раздел 5).

Кнопки «Start setup» в PDF и письме ведут не на регистрацию, а обратно на чекер
(`/?resume=…`), поэтому обойти пейвол по ссылке из письма нельзя.

Если Stripe-ключи на сервере не заданы, пейвола нет и «Start setup» ведёт прямо
на регистрацию, как раньше (без `opening`).

На пейволе есть поле «Промокод»: код может снизить комиссию или обнулить её
(тогда PaymentIntent не создаётся, а токен выдаётся сразу). Подробно: раздел 9.

## 3. Параметры URL, которые получает регистрация

**Новые:**

| Параметр | Пример | Что это |
|----------|--------|---------|
| `opening` | `v1.eyJwaSI6….Q2x…` | подписанный токен оплаты (раздел 4); при промокоде внутри есть поле `promo`, а при бесплатном коде `pi = cus_…` (раздел 9) |
| `email` | `jane@northwind.co.uk` | рабочий e-mail с пейвола (на него ушла квитанция Stripe; при бесплатном коде квитанции нет) |

`company` и `company_number` после пейвола **не приходят**: пейвол их больше не
спрашивает.

**Существующие (без изменений):** `plan`, `country`, `industry`, `services`,
`corridors_in`, `corridors_out`, `crypto`, `utm_source`, `utm_medium`,
`utm_campaign`, `utm_term`, `utm_content`.

`volume_in`, `volume_out`, `tx_in`, `tx_out` с 2026-09-23 **не приходят**: чекер
спрашивает объём и число транзакций одной общей цифрой (входящие и исходящие
вместе), а KYB собирает их по направлениям сам. `corridors_in` и `corridors_out`
несут один и тот же список: коридоры чекер тоже спрашивает один раз.

Пример:

```
https://app.altery.com/n/registration-corporate?plan=pro&country=GB&industry=1115
  &services=local-payments,cards&corridors_in=uk-eea,US&corridors_out=uk-eea,US
  &email=jane%40northwind.co.uk&opening=v1.eyJwaSI6InBpXzNQ…&utm_source=google
```

Доверять можно **только** `opening` (он подписан). `email` и `country` —
удобство для предзаполнения, их можно подменить руками в адресной строке.
Подписанная страна — `cc` внутри токена.

## 4. Токен `opening`

Формат: `v1.<payloadB64url>.<sigB64url>` (base64url без `=`).

```json
{ "pi": "pi_3Pxxxxxxxx", "cc": "GB", "iat": 1790000000, "lm": true }
```

С промокодом (раздел 9) добавляется поле `promo`; при бесплатном коде вместо
PaymentIntent в `pi` стоит id объекта Customer:

```json
{ "pi": "pi_3Pxxxxxxxx", "cc": "GB", "iat": 1790000000, "lm": true, "promo": "HALF" }
{ "pi": "cus_Rxxxxxxxxx", "cc": "GB", "iat": 1790001000, "lm": true, "promo": "FREE100" }
```

| Поле | Значение |
|------|----------|
| `pi` | id PaymentIntent в Stripe (`pi_…`): ключ платежа, по нему регистрация привязывает оплату к заявке (раздел 5). При бесплатном промокоде — id Customer (`cus_…`), запись о применении кода; правило то же |
| `cc` | страна регистрации компании из опроса чекера, ISO 3166-1 alpha-2 |
| `iat` | время создания платежа (или записи Customer), unix-секунды |
| `lm` | `true` — боевой платёж Stripe (live mode), `false` — тестовый (test mode, карта `4242…`) |
| `promo` | только при промокоде: сам код (`[A-Z0-9_-]{3,32}`). Без кода поля нет вовсе, и токен байт в байт такой же, как до появления промокодов |

Компании в токене нет: в момент оплаты она неизвестна. Токен доказывает одно:
за эту попытку заявки заплачено £100 (или применён промокод, раздел 9).

Подпись: `HMAC-SHA256(OPENING_FEE_TOKEN_SECRET, "v1." + payloadB64url)`.
Секрет общий у чекера и регистрации (передаётся через secret-store, не в чате),
**минимум 32 символа** (`openssl rand -hex 32`) и **свой в каждом окружении**:
продовый секрет не задаётся на staging, preview или локально.
Токен детерминирован: для одного платежа всегда один и тот же токен.
**Срока жизни нет** (по политике оплата не истекает), `iat` проверять на
«свежесть» не нужно.

**`lm` проверять обязательно.** Тестовая оплата ничего не стоит, поэтому
продовая регистрация принимает только `lm === true`. Поле внутри подписи, так
что «перекрасить» тестовый токен в боевой нельзя. Это страховка на случай,
если продовый секрет всё-таки окажется в тестовом окружении. Staging-регистрация
(с тестовыми ключами и своим секретом) включает `allowTestMode`.

Проверка (Node 18+, без зависимостей). Этот блок тест
`test/openingFee.test.mjs` запускает как есть на токенах, которые выдаёт
чекер, так что код ниже заведомо рабочий:

<!-- verify-snippet: test/openingFee.test.mjs исполняет следующий js-блок и сверяет его с lib/opening-fee-token.js. Менять вместе. -->
```js
import crypto from "node:crypto";

const B64URL_RE = /^[A-Za-z0-9_-]+$/;

// Возвращает { pi, cc, iat, lm, promo? } или null (подделка, чужой секрет, мусор).
// pi — "pi_…" (оплата) или "cus_…" (бесплатный промокод); promo есть только при коде.
// allowTestMode: true — только в staging. В проде токен тестовой оплаты = не оплачено.
export function verifyOpeningToken(token, secret, { allowTestMode = false } = {}) {
  if (typeof token !== "string" || token.length > 1024 || !secret) return null;
  const parts = token.split(".");
  if (parts.length !== 3 || parts[0] !== "v1") return null;
  const [, body, sig] = parts;
  if (!B64URL_RE.test(body) || !B64URL_RE.test(sig)) return null;
  const given = Buffer.from(sig, "base64url");
  if (given.toString("base64url") !== sig) return null; // ровно одна строка на платёж
  const expected = crypto.createHmac("sha256", secret).update("v1." + body).digest();
  if (given.length !== expected.length || !crypto.timingSafeEqual(given, expected)) return null;
  let p;
  try { p = JSON.parse(Buffer.from(body, "base64url").toString("utf8")); }
  catch { return null; }
  if (!p || typeof p.pi !== "string" || !/^(?:pi|cus)_[A-Za-z0-9]{8,}$/.test(p.pi)
      || typeof p.cc !== "string" || !/^[A-Z]{2}$/.test(p.cc)
      || !Number.isInteger(p.iat) || p.iat <= 0 || typeof p.lm !== "boolean"
      || (p.promo !== undefined && (typeof p.promo !== "string" || !/^[A-Z0-9_-]{3,32}$/.test(p.promo)))) return null;
  if (p.lm !== true && !allowTestMode) return null;
  const out = { pi: p.pi, cc: p.cc, iat: p.iat, lm: p.lm };
  if (p.promo !== undefined) out.promo = p.promo;
  return out;
}
```

На другом языке: HMAC-SHA256 от ASCII-строки `"v1." + payloadB64url`, сравнить
с base64url-декодированной подписью постоянным по времени сравнением, затем
проверить форму payload (`pi`, `cc`, `iat`, `lm`, необязательный `promo`) и
`lm === true`.

## 5. Что должна сделать регистрация

Обязательно:

1. **Проверить токен** `opening` (раздел 4): подпись HMAC общим секретом и, в
   проде, `lm === true`. Невалидный или отсутствующий токен, а в проде и токен
   с `lm: false` = оплата не подтверждена (заявку не считать оплаченной,
   пометить для операций).
2. **Одна оплата = одна заявка, привязка при первом использовании.** Сохранить
   `pi` из токена на заявке в поле с **UNIQUE-ограничением** (рядом можно
   хранить и сам `opening` строкой, как пришёл). Первая заявка, пришедшая с
   этим `pi`, забирает оплату: компания из этой заявки и есть компания, за
   которую заплачено. **Вторую заявку с тем же `pi` не принимать:** показать
   заявителю понятное сообщение и направить в поддержку. Пример текста (на
   языке интерфейса регистрации):

   > This payment has already been used for another application. Each
   > application needs its own opening fee. If you think this is a mistake,
   > contact us at sales@altery.com.

   (`sales@altery.com` — тот же адрес поддержки, что показывает чекер,
   ключ `ec.support.email`.)

   - Проверять **ограничением в базе**, а не только чтением «есть ли уже
     заявка»: две вкладки или двойной клик могут прислать один токен
     одновременно, и выиграть должна ровно одна заявка.
   - Повторный переход по той же ссылке **тем же заявителем** (перезагрузка,
     возврат после 3-D Secure, ссылка, которую прислала поддержка) — не вторая
     заявка: открыть его существующую заявку, а не отказывать.
   - `pi` может быть и `cus_…` (бесплатный промокод, раздел 9). Хранить и
     проверять на уникальность **точно так же**: одно применение кода = одна
     заявка. Поле `promo` из токена удобно сохранить рядом (и показать
     операциям): оно говорит, что за заявку не платили или платили со скидкой.

Удобство:

3. Предзаполнить e-mail из `email` (параметр не подписан, это только подсказка).

По желанию:

4. Если страна регистрации компании в заявке **не равна** `cc` из токена,
   пометить заявку для операций: в чекере клиент указал другую страну (ошибся в
   опросе или оплата досталась не той компании).

Ходить в Stripe регистрации не нужно: подпись уже означает, что сервер чекера
проверил успешный платёж £100.

## 6. Операции: как найти платёж

Компании в Stripe **нет**: она становится известна только в регистрации, и
связь «платёж ↔ компания» — это `pi` на заявке. Искать платёж:

- **По заявке:** взять `pi` из заявки (или из токена: base64url-декод средней
  части) и открыть `https://dashboard.stripe.com/payments/<pi>`.
- **По клиенту:** строка поиска в Dashboard принимает id `pi_…` и e-mail.
- **Точно по metadata** (Search API, индекс обновляется с задержкой до ~1 мин;
  e-mail сохранён в нижнем регистре, искать так же):

```bash
curl -G https://api.stripe.com/v1/payment_intents/search \
  -u "$STRIPE_SECRET_KEY:" \
  --data-urlencode "query=metadata['email']:'jane@northwind.co.uk'"
```

Metadata каждого платежа: `kind=account_opening_fee`,
`source=altery-eligibility-checker`, `email`, `company_country`, `plan`,
`entity`, `lang`, `terms_version`, `terms_accepted_at`. Описание платежа:
«Altery account opening fee». Названия и номера компании в metadata нет.
У платежа со скидкой по промокоду добавлены `promo_code`, `promo_id`,
`original_amount` (10000) и `discount_amount`; `amount` такого платежа меньше
£100. Бесплатных применений кода среди платежей **нет**: их искать среди
Customers (раздел 9).

Если регистрация ответила клиенту «оплата уже использована», а клиент с этим
не согласен: найти в регистрации заявку, которая забрала этот `pi`, и сверить
её e-mail с `metadata.email` платежа. Дальше решают операции вручную.

Возвратов по политике нет. Если руководство всё же разрешит возврат в порядке
исключения, делать его вручную в Dashboard и **вручную пометить заявку**,
к которой привязан этот `pi`: токен о возврате не знает и продолжит проходить
проверку.

## 7. Настройка Stripe Dashboard

1. **Ключи:** Developers → API keys. На сервер: `STRIPE_SECRET_KEY` (можно
   restricted-ключ `rk_…` с правом записи PaymentIntents) и
   `STRIPE_PUBLISHABLE_KEY` (`pk_…`), одного режима (test или live).
   Плюс `OPENING_FEE_TOKEN_SECRET` (`openssl rand -hex 32`; короче 32 символов
   пейвол не включится), отдельный для прода и для каждого тестового окружения.
   См. `docs/DEPLOY.md`, раздел 4 и 7.8.
2. **Квитанции:** Settings → Customer emails → включить «Successful payments».
   Без этого `receipt_email` не отправляется. В test-режиме Stripe квитанции сам
   не шлёт.
3. **Statement descriptor:** Settings → Public details, чтобы в выписке клиента
   платёж читался как Altery (меньше chargeback «не узнаю платёж»).
4. **Apple Pay и Google Pay: зарегистрировать домен.** Пейвол принимает карту,
   Apple Pay и Google Pay. Кошельки идут поверх типа `card`, поэтому
   PaymentIntent по-прежнему создаётся с `payment_method_types: ["card"]`, и
   отдельные методы в Dashboard включать не нужно. Но кнопки кошельков Stripe
   показывает **только на домене, зарегистрированном в Stripe**, и только по
   HTTPS; на `localhost` их не будет никогда (там только поле карты, это
   нормально). Регистрация: Dashboard → Settings → Payment methods → Payment
   method domains → добавить домен, или через API (нужен ключ с доступом к
   Payment method domains; restricted-ключ сервера из п. 1 такого права может
   не иметь, тогда проще через Dashboard):

   ```bash
   curl https://api.stripe.com/v1/payment_method_domains \
     -u "$STRIPE_SECRET_KEY:" \
     -d domain_name=<домен чекера>    # без https://, например check.altery.com
   ```

   Прод-домен чекера **ещё не выбран**, поэтому это шаг выката
   (`docs/DEPLOY.md`, раздел 9): зарегистрировать домен сразу, как он
   зафиксирован, и так же каждый другой домен, где открывают пейвол
   (staging). После регистрации проверить в Dashboard, что для домена Apple Pay
   и Google Pay активны.
5. **Stripe Link сознательно выключен** в интерфейсе пейвола
   (`checker-paywall.jsx`). Это решение, а не поломка.
6. **Страна плательщика.** Страну для оплаты (billing country) клиент выбирает
   в нашем собственном селекторе стран на пейволе, и она передаётся в Stripe.
   Это страна карты, она может не совпадать со страной компании (`cc`).

## 8. Ответы API (для разбора обращений)

| Код | Когда |
|-----|-------|
| `400 promo_invalid` | `create` с промокодом, которого нет, который выключен, истёк или не подходит к комиссии в GBP |
| `400 promo_used` | `create` с промокодом, который этот e-mail уже применял |
| `402 not_paid` | платёж ещё не прошёл (`status` в ответе, например `processing`) |
| `404 not_found` | такого платежа нет, это не наш сбор, или скидка в metadata платежа не сходится с его суммой |
| `429` | лимит частоты: `create` 5/мин и 20/час с IP, 5/час на один e-mail; `confirm` 20/мин и 120/час с IP; проверка промокода (`promo`) 10/мин и 30/час с IP |
| `502 stripe_error` | Stripe недоступен или отказал (подробности только в логах сервера); для проверки кода это тоже 502, а не «код недействителен» |
| `503 not_configured` | на сервере не заданы Stripe-переменные |

Проверка промокода отвечает `200 {valid:false, reason}` с `reason` = `invalid`
(нет такого кода, выключен, неверный формат), `expired` (истёк срок или купон
исчерпан) или `used` (этот e-mail уже применял код; только если e-mail был
передан).

Если клиент пишет, что деньги списались, а регистрация не открылась: найти
платёж по e-mail (раздел 6) и получить тот же токен ещё раз (для одного
платежа он всегда одинаковый):

```bash
curl -s -X POST https://<домен чекера>/api/opening-fee \
  -H 'Content-Type: application/json' \
  -d '{"action":"confirm","paymentIntentId":"pi_…"}'
# → {"ok":true,"token":"v1.…","email":"…","country":"GB","plan":"pro","entity":"uk"}
```

Затем выслать клиенту ссылку на регистрацию с `opening=<token>` и `email`.
**Повторно платить клиенту не нужно.** Если заявка с этим `pi` уже создана,
клиент продолжит её (раздел 5, п. 2).

Для бесплатного применения промокода такого способа пока нет: токен выдаётся
один раз в ответе на `create`, а `confirm` принимает только `pi_…`. Если клиент
потерял ответ (обрыв связи ровно в этот момент), запись Customer уже создана
и повторная попытка ответит «код уже использован»; операции находят Customer
по e-mail (раздел 9) и решают вручную (например, удаляют запись, чтобы клиент
применил код ещё раз).

## 9. Промокоды

Решение основателя (2026-09-23): на пейволе под полем e-mail есть поле
«Промокод (необязательно)». Коды живут **в Stripe**: Dashboard → Product
catalog → Coupons → купон → Promotion codes. Сегодня есть один: `FREE100`
(купон 100 %, `duration: once`, без срока и без общего лимита).

**Правило:** один человек применяет код один раз. Человек = рабочий e-mail,
введённый на пейволе (в нижнем регистре, без пробелов по краям).

Stripe **не умеет** применять promotion code к PaymentIntent (это функция
Checkout и подписок), поэтому код проверяет и скидку считает наш сервер
(`lib/opening-fee-promo.js`), а правило «один раз на человека» тоже держим мы.

### Как это работает

1. Клиент вводит код и нажимает «Применить» (или Enter). Чекер шлёт
   `POST /api/opening-fee {action:"promo", code, email?}`. Сервер ищет код в
   Stripe (`GET /v1/promotion_codes?code=…&active=true&limit=1`), сам считает
   сумму комиссии и, если e-mail уже введён, проверяет по учёту (ниже), не
   применял ли этот e-mail этот код. Ответ:
   `{valid:true, code, percentOff, amountOff, amount, display, free}` либо
   `{valid:false, reason:"invalid"|"expired"|"used"}`. Сумму клиент только
   показывает: сервер от клиента сумму не принимает.
2. **Бесплатный код** (`free: true`: комиссия ниже минимума Stripe в 30 p, для
   `FREE100` ровно £0). На пейволе скрываются страна плательщика, форма карты и
   галочка согласия (платежа нет, соглашаться нечего), в блоке «Your costs»
   £100 зачёркнуто и стоит £0 с подписью «Free with code FREE100», кнопка
   становится «Continue to application». `create` с `promoCode` **не создаёт
   PaymentIntent**: сервер повторно проверяет код и e-mail, создаёт запись о
   применении (Customer, ниже), выдаёт токен и отвечает
   `{free:true, token, email, country, plan, entity, promo}`. Дальше тот же
   успешный экран и тот же переход в регистрацию с `opening` и `email`.
3. **Частичная скидка** (сумма ≥ 30 p). Обычный платёж картой, но
   PaymentIntent создаётся на сумму со скидкой, а в его `metadata` добавлены
   `promo_code`, `promo_id`, `original_amount` (10000) и `discount_amount`.
   `confirm` принимает такой платёж только если `original_amount` = 10000 и
   `amount` = `original_amount − discount_amount`; иначе `404 not_found`. После
   успешного `confirm` сервер записывает применение (один раз на платёж) и
   добавляет `promo` в ответ и в токен.
4. Если между проверкой и оплатой код успели применить с этим e-mail (или
   выключили в Stripe), `create` отвечает `400 promo_used` / `400 promo_invalid`;
   пейвол снимает код, и комиссия снова полная.

### Учёт применений

У сервера нет базы, а Stripe уже хранит деньги, поэтому каждое применение
кода — **объект Customer в Stripe**: `email` = e-mail клиента, описание
«Account opening fee promo redemption», metadata: `kind = opening_fee_promo`,
`source = altery-eligibility-checker`, `promo_code`, `promo_id`,
`promo_redeemed_at` (ISO), `company_country`, `plan`, `entity`, `lang` и, для
частичной скидки, `payment_intent`. Бесплатное применение платежа не имеет, и
именно id этого Customer (`cus_…`) стоит в токене как `pi`.

- **Найти:** Dashboard → Customers → поиск по e-mail. Или
  `GET /v1/customers?email=jane@northwind.co.uk` (e-mail в нижнем регистре).
  Клиент «уже применял код», если среди его Customers есть запись с
  `metadata.kind = opening_fee_promo` и этим `promo_code`. Один e-mail может
  применить разные коды (по одной записи на каждый).
- **Снять применение** (только в порядке исключения): удалить этот Customer в
  Dashboard. Уже выданный токен продолжит проходить проверку подписи;
  заявку с этим `pi` (`cus_…`) при необходимости пометить в регистрации
  вручную.
- **Счётчик Stripe `times_redeemed` не растёт:** в терминах Stripe код никто не
  «применяет». Наш счётчик — `metadata.redemptions` на самом промокоде
  (Dashboard → Promotion codes → код → Metadata), обновляется best-effort
  после каждого применения и может отставать на единицу при одновременных
  применениях. Источник истины — записи Customer.
- По той же причине **`max_redemptions` промокода в Stripe сам не сработает**:
  общий лимит применений держать вручную (выключить код, когда счётчик дошёл
  до нужного числа).
- Запись для бесплатного применения создаётся с ключом идемпотентности,
  единым для пары (e-mail, код): две вкладки, применившие один код для одного
  адреса одновременно, получают **одну** запись и один токен.

### Как завести или выключить код

1. Dashboard → Product catalog → Coupons → New coupon: процент (`percent_off`)
   или сумма **в GBP** (`amount_off`; купон в другой валюте пейвол считает
   недействительным). `Duration: once`. Лимиты и срок купона (`redeem_by`,
   `max_redemptions`) учитываются: истёкший или исчерпанный купон даёт
   `expired`.
2. В купоне → Promotion codes → Add: сам код (латиница, цифры, `-`, `_`; от 3
   до 32 символов; регистр не важен), при желании срок (`expires_at`).
   Ограничения `first_time_transaction` / `minimum_amount` пейвол **не
   проверяет**.
3. Проверить на пейволе: ввести код → «Применить» → зелёная строка «FREE100
   applied: account opening fee £0».
4. Выключить: Promotion code → Deactivate (клиенту покажется «код
   недействителен»; код с прошедшим `expires_at` покажет «срок действия истёк»).
